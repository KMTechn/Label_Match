7. **제품이 모자란 트레이(드묾)** ◆
   - **새 현품표**: 옛 수동 마감(PARTIAL)은 LOCAL·ONLINE 모두 거절한다. 새 현품표 재스캔은 회사 서버에서 확인한 현재 작업군 멤버 수가 1–3이고 찍은 제품 수와 같을 때만 완료한다(원 TRANSFER 봉인 수와 구별). 멤버 수를 모르면 「서버 연결 뒤 마감」, 수가 다르면 「모자란 상자: 대체품으로 채워 정상 마감 — 못 채우면 마감하지 말고 따로 두고 관리자에게」를 보이고 현재 상자를 유지한다. 설정된 표본 수의 정상 자동 완료는 유지한다. 부족 조건이 맞는 새·옛 현품표는 부분 제출을 확인한 뒤 유예 없이 확정한다.
     - 까닭: 포장 앱은 표본 4개만 찍어 실제로 담긴 제품을 모른다. 회사 웹은 포장 길에서 「미달」 표시를 읽지 않고 봉인된 이적 묶음 전량으로 포장한다(웹 `service.py:12810-12860`·`packages.py:1672-1760`, webux 10/11 02:31 코드 읽기). 그래서 모자란 트레이가 **전량으로 출고돼 수량이 실물보다 많아진다**. 앱에서 막는다. 웹도 포장 길의 미달 표시를 거절하게 고친다(웹 WEB-N4, 10/19 판).
   - **옛 현품표**: 제품을 1개 이상 찍은 뒤 같은 현품표를 다시 찍으면 부분 제출을 묻는다(F-25). 같은 현품표·빈 Enter·부분 제출 단추는 즉시 확정하고, 계속 작업·Esc는 확인만 내린다(F-26). 제품·다른 현품표는 확인을 내린 뒤 기존 스캔 처리를 한다. 부분 제출 뒤에는 되돌리지 않는다.
8. **회사 서버가 끊겨도 계속**: 입력을 막지 않는다.
   - 바닥 줄이 「회사 서버 연결 안 됨 · 이 PC에 저장 중 · 보낼 것 N건」(주황)으로 바뀐다(F-52).
   - 다시 연결되면 저절로 보낸다(F-33·F-64·F-65).
   - 회사 서버가 그 트레이만 거절하면 그 트레이만 보류하고 다른 트레이는 계속한다(F-34).
9. **다시 켰을 때**: 날짜가 바뀌어도 하던 트레이를 묻지 않고 그대로 이어 준다(F-39·F-40). 위 안내 줄에 「어제 하던 세트를 이어서 엽니다 — 세트 이름·남은 N개」가 보이면 그대로 이어 한다. 읽을 수 없는 세트는 따로 보존하고 관리자 확인을 기다린다. 안전하게 따로 보관하지 못하면 새 작업도 기다린다.
10. **한 단계 안의 화면**: 오른쪽 탭에서 본다(F-43·F-49·F-51). 작업 화면에 늘 띄우지 않는다.
    - 「진행 현황」: 오늘 출고 계획 대비 남은 수.
    - 「이번 작업」·「스캔 기록」·「통과 요약」. 스캔 기록은 새 화면·비상 옛 화면 모두 오늘 최근 100줄만 보인다. 지난 기록은 회사 웹 리포트에서 본다.
    - 탭에서 스캔하면 작업 화면으로 돌아와 그대로 처리한다(F-44).
11. **하루 끝**: 따로 할 일 없다. 하던 트레이가 있으면 닫을 때 한 번 묻는다(F-66). 관리자의 원격 멈춤 요청은 확인 창 없이 하던 트레이를 저장하고 같은 정상 종료를 진행한다([절차](operations.md#remote-app-stop)).

### 3-3. 관리자 메뉴 (작업 화면에서 뺀 것)
- 「멈춘 작업 확인」(F-55): 목록 보기는 PIN이 없고, 작업/관리자 동작을 아래처럼 나눈다.
  - 「같은 요청 다시 확인」(F-56): 기준일에는 관리자 PIN 유지(일반 조회/복원 분리는 첫 업데이트).
  - 「보류 후 계속」(F-57): 작업자, PIN 없음.
  - 「지원 인계」(F-58): 작업자, PIN 없음. 관리자 요청의 승인 상태를 바꾸지 않고 인계 사실만 기록한다.
  - 「실물 현품표 스캔·회사 서버 조회」(F-59): 작업자, PIN 없음. 기존 회사 서버 근거·CAS를 유지한다.
  - 「관리자 확인 다시 조회」·「이 건만 보류하고 다른 작업 계속」(F-60)
  - 「변경 파일 원위치 복원」(F-61): 관리자 PIN 유지.
- PIN 확인이 거절되거나 끊겨도 「이 건만 보류하고 다른 작업 계속」을 선택할 수 있다. 대상·작업자 변경이나 감사 저장 실패 때는 보류하지 않는다. 원본과 요청 키를 보존하고 다른 현품표의 스캔을 받으며, 보류된 현품표는 관리자 확인 전까지 다시 처리하지 않는다.
- 관리자 동작의 PIN은 화면에서 받고, 회사 서버 확인과 이 PC 적용은 기존 배경 처리 순서로 진행한다. 같은 대상의 중복 누름은 막고, 창이 닫혀도 이미 승인된 적용은 끝까지 한다. 상세는 [operations.md](operations.md#package-admin-pin-ui-lane).
- 「대기 현황」 탭(F-50)과 바코드 원문 복사(F-45)는 다음 판에서 이 메뉴로 옮긴다(§7 LM-10·LM-11).

  - 옛 현품표 받기로 끝낸 트레이는 회사 서버 포장 기록 없이 이 PC 기록 파일로만 올라간다(F-15).

## 8. 실제 PC 작동 확인 방법
### 8-1. 설치
- 설치기는 고정 `kmtech_shared` 0.3.8 PowerShell leaf를 manifest/leaf pin 확인 뒤 호출한다([X13-B](operations.md#shared-powershell-x13b)). manifest 크기 조회는 숨김 파일을 포함하고 기존 provider 경로·JSON 오류·64KiB 한도를 유지한다. 런타임 PowerShell 파일과 생성 템플릿은 OS 모듈의 절대 경로 import 두 줄로 PS7 상속 경로 오염을 막는다. 자료 세대 UNKNOWN 원인은 비공개 속성으로 보존하며 진단 로그 잎은 공급만 하고 앱에 연결하지 않는다([고정 shared core](operations.md#shared-core-x04b)).
- **목표: 관리자 SSH 숨김 설치·업데이트로 깔린다(현장 PC 화면에 설치 창·Windows 허용 창 0).**
- **제품 후보(w9firstupdsub63)**: 상승/Session 0 입구는 키트가 넘긴 작업자 계정과 그 작업자의 READY inventory를 먼저 확인한다. 작업자 인수를 생략한 상승 SSH 호출은 안정된 활성 콘솔 작업자를 확인한다. 기계 몫을 배치한 뒤 `PASS_MACHINE_WORKER_PENDING`으로 작업자 첫 시작을 기다리며, 호출자와 작업자 SID가 같아도 상승 SSH에서 사용자 프로필·등록·Run을 준비하지 않는다. 지정 작업자의 기존 일반 세션 onboarding이 READY를 확인해야 작업자 HKCU에 완료가 기록된다.
  - 키트 관리자 가지 연결·실제 Windows 설치/되돌림은 아직 미증명이다(LM-2). 현장 일반 세션 설치는 기존 Windows 허용 창 승인을 사용한다.

## 107 회수 증거의 시작 판정

107은 거절 길의 논리 내용 그대로를 보존한다. 원 업무 행·CREATE/CANCEL 영수증·완료 표지·회수 증거를 지우거나 다시 써서 시작을 허용하지 않는다. 기존 연결 정리의 WAL checkpoint 경로는 유지하며, 물리 파일 보존을 위한 읽기 전용 admission 분리는 첫 업데이트 범위다.

JSON·관계·자료형·필수 키 실패는 `PACKAGE_RECOVERY_STORED_EVIDENCE_INVALID`, 정상 증거 조회 중 저장소 실패는 별도 `PACKAGE_RECOVERY_STORAGE_UNAVAILABLE`로 거절한다. SQL에 넘길 snapshot 식별자는 조회 전에 검사한다. 저장소 오류는 「작업 기록을 읽지 못했습니다」/「잠시 후 프로그램을 다시 켜세요」와 작은 줄 「코드: PACKAGE_RECOVERY_STORAGE_UNAVAILABLE」를 보인다. 기존 안내에는 자세히 칸이 없어 「다시 켜도 같으면 현장 관리자에게 알리세요」를 보조 줄로 표시한다(WMX0008–0009). 원 오류 내용은 안내에 넣지 않는다. 두 코드는 기존 시작 거절 관측과 정해진 종료로 연결한다.

정상 회수 증거의 양성 회귀는 실제 `main`·guarded callback·store admission을 지나며 UI·네트워크·외부 상태만 격리한다. 실제 GUI 수용 회차를 대신하지 않는다. 읽기 계약의 정본은 별도 [package-recovery.md](package-recovery.md)의 지정 바이트 그대로 유지한다.


v2.0.107 조립: 앱 판·자료 판·하한 모두 107. field-update-feed 원본 SHA 결속과 ZIP runtime 관문은 [운영](operations.md#v20107-조립-관문), machine-worker 예외는 [lifecycle 설계](LIFECYCLE-DESIGN.md)를 따른다.

복구 GUI가 요청한 상주 전송은 원래 시작 경계를 유지해 같은 판·계정의 일반 relay 하나를 시작하거나 살아 있는 relay를 재사용한다. 부모 GUI만 있다는 이유로 성공을 반환하지 않으며, 증명 실패 때는 기존 진행 안내를 유지한다. [복구 relay 계약](contracts.md#ordinary-recovery-relay-bootstrap)을 따른다.


G41/G45: 일반 복구 증명이 검사한 행으로 relay를 하나로 유지하고, 지정된 복구 상태에서 relay만 남았으면 같은 검증 경계로 GUI 하나를 시작한다. [일반 GUI 복구 cohort](contracts.md#ordinary-recovery-gui-cohort)와 ROLLBACK_PENDING의 앞 판·일반 relay·자료 세대 증명 조건을 따른다.
